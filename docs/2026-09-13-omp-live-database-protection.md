# Protect OMP's open SQLite file locks

## Evidence and scope

On this Linux WSL2 host, OMP 18.1.18 bundles Bun 1.4.2 and SQLite 3.53.2. Its sqlite-reader.ts `HTa` helper calls `Bun.file(path).slice(18,20).bytes()` before opening a SQLite read connection; file identification also reads a header. Closing such an independently opened descriptor releases POSIX process-associated locks held on the same inode. A synthetic two-writer reproduction using this exact OMP binary retains four committed rows without that header read but only three with it; all SQL writers exit zero. The previous real OMP session invokes read on its own agent.db at 2026-09-12T20:22:34.712Z and on agent.db:auth_credentials at 20:22:42.366Z. These facts establish a reproducible unsafe operation and a matching real trigger, not proof that every corrupted page came from it. Current agent.db has 42 pages but its valid header declares 46; the older corrupt agent.db has 453 pages versus 455 declared.

SQLite documents this mechanism in [POSIX advisory locks canceled by a separate thread doing close](https://sqlite.org/howtocorrupt.html#posix_advisory_locks_canceled_by_a_separate_thread_doing_close_). Concurrent SQLite connections alone are not the defect. The ordinary file open/close bypasses SQLite's descriptor tracking and releases locks outside its knowledge.

The synthetic syscall trace records the control writer's attempted exclusive lock on the database shared-lock range failing with EAGAIN. With the header read, a Bun thread opens and closes an extra descriptor for the same database, the other writer successfully acquires the exclusive lock, and it unlinks both WAL and SHM while the original connection remains open. Both external writers exit zero, yet the first reproduction retains three rows instead of four. Adding an index creation in the second writer reproduces `database disk image is malformed (11)` on the final integrity check, while the control still passes with four rows. This demonstrates both silent committed-row loss and structural corruption under the exact installed runtime. It does not uniquely attribute the real file's missing tail pages to this mechanism. Synthetic evidence is kept outside the repo at `/tmp/omp-recovery-2026-09-13-1rlPJSqo/lock-repro.ts`, `lock-repro.trace` (earlier row-loss version), and `lock-repro-corruption.trace` (final malformed-database version), with no user credentials in these artifacts.

## Recovery

The official SQLite 3.53.4 tools ZIP matches the published SHA3-256 checksum `6eeb57e8f2aef7687f9f016a980992cf2799c8c07a87c5e21495530f91915047`. Its `.recover --ignore-freelist` salvages current agent.db with three valid JSON credential records (Anthropic, OpenAI Codex, and Z.ai), and full integrity_check returns ok. Reindexing a copy of history.db fixes two missing index entries while retaining 563 rows; its external-content FTS integrity check also passes. The restored originals and their sidecars remain in `~/.omp/recovery-2026-09-13/`. Models.db already passes integrity checks and is not replaced. Provider authentication is not exercised as part of data validation.

Yesterday's preserved corrupt credential database also recovers successfully into a separate database, containing six provider records. Do not automatically merge older OAuth credentials into the current database: token rotation and later user changes may make older records stale.

## Exact changes

Add `omp/.omp/agent/extensions/protect-live-sqlite.ts` and `tools/tests/protect-live-sqlite.test.ts`. Do not modify existing extensions, model routing, shell configuration, or compiled OMP. Default export `protectLiveSqlite(pi: ExtensionAPI): void`, using a type-only import from `@oh-my-pi/pi-coding-agent`. On Linux register a `tool_call` handler. Only handle event.toolName === 'read' and typeof event.input.path === 'string'. Before execution call the helper below with ctx.cwd. When protected, return `{ block: true, reason: 'This SQLite file is already open by OMP. Reading it through this tool can release OMP’s Linux file locks and corrupt state. Inspect it with sqlite3 in a separate bash process instead.' }`; otherwise return undefined. Non-Linux registers no hook because /proc is Linux-specific. This is a hard rejection of an unsafe same-process operation, never an automatic reroute, recovery, or fallback.

Export `isOpenSqlitePath(rawPath: string, cwd: string): Promise<boolean>` as the helper used by the handler and tests. Use node:fs/promises `readdir`, `readlink`, and `stat`, node:path `resolve`, and node:os `homedir`. No reads of file contents. Enumerate `/proc/self/fd`; readlink each fd. Only consider fd targets ending in `.db`, `.sqlite`, `.sqlite3`, or their `-wal`/`-shm` sidecars (strip trailing ' (deleted)' before matching). Stat those fd paths with bigint:true and collect `${dev}:${ino}` keys. Ignore only ENOENT for fd races; propagate other IO errors. Enumerating/statting descriptors does not close SQLite’s underlying descriptors.

Build path candidates from the exact rawPath and every prefix ending immediately before a `:` or `?` (selectors and query suffixes). Resolve ~ and ~/ with homedir; other paths resolve against cwd. Stat each candidate with bigint:true; return true on any matching dev/ino. Ignore only ENOENT and ENOTDIR for candidate paths; propagate others. Symlinks resolve naturally through stat, and inode comparison also handles hard links. Do not open target files, use Bun.file, load SQLite, or inspect credentials. Tests create open bun:sqlite databases in temp directories and verify protection for direct paths, selectors, relative paths, ~ where practicable, symlink/hardlink aliases, and open WAL sidecars. Ordinary closed database paths and unrelated text paths are not blocked. Ensure all fixtures close database connections before deleting temp dirs.

Run `bun test tools/tests/protect-live-sqlite.test.ts` and `git diff --check`. No suppressions, comments, new dependencies, broad catches, speculative APIs, or hidden fallbacks. The existing stow extension symlink makes this addition available to default, mix, and china profiles when installed in the canonical dotfiles tree; no re-export or existing call-site edits are required. CLI standalone `omp read`, --no-extensions sessions, directory-wide file scans, and arbitrary extension file IO remain outside this specific tool_call boundary and must be reported as limitations.
